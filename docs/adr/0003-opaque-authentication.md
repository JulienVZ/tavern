# ADR 0003 — OPAQUE for password authentication

- Status: accepted
- Date: 2026-11-13

## Context

The instance admin is part of the threat model: a curious admin, or anyone who compromises the server, must not learn user passwords. Users reuse passwords, and the same password may also protect key material. Sending the password to the server, even over TLS and even hashed client-side with a fixed salt, gives the server a password-equivalent value.

## Decision

Use **OPAQUE** (RFC 9807) through the **`opaque-ke`** crate (4.0), with:

- ristretto255 for the OPRF and key exchange groups, Triple-DH as the key exchange, SHA-512;
- **Argon2id** as the key stretching function (feature `argon2`), parameters fixed in the `crypto` crate and benchmarked on low-end hardware at M1;
- the handle as credential identifier.

Server side:

- The OPAQUE `ServerSetup` is an instance secret generated by `deploy/scripts/init.sh`. Losing it invalidates every password; it is part of the backup set.
- Login for an unknown handle runs against a dummy record so that responses do not reveal whether an account exists.
- The state between the two login round trips is kept in memory for a short time (60 s), keyed by a random login id.
- After a successful login the server issues a random 256-bit session token, stores only its SHA-256 hash, and binds it to a device. Tokens are revocable.
- TOTP (optional, `totp-rs`) is checked after OPAQUE succeeds and before a session is issued. Passkeys come later.
- All authentication routes are rate limited per IP and per handle.

Client side, the OPAQUE **export key** (derived from the password, never known to the server) protects the account identity key:

- At registration the client generates the Ed25519 account identity key (AIK) and a random 256-bit recovery key. It uploads the AIK public key and two wrapped copies of the AIK private key: one under a key derived from the export key, one under the recovery key (XChaCha20-Poly1305 in both cases).
- At login on a new device, the client unwraps the AIK with the export key, signs the new device's certificate, then erases the AIK private key from memory. It is not stored on the device.
- **Password strength is enforced on the client**, since the server never sees the password: at registration and at every password change the client requires at least 12 characters and a strength estimate of 3 out of 4 or better (zxcvbn-style estimator, run locally, fed with the handle and display name as penalised words). The UI explains why: the password also protects the account identity key.
- **Every device enrolment is announced.** The server sends `DeviceListChanged` to all existing devices of the account, which show a notification naming the new device and offering to revoke it. Contacts see a visible notice ("Alice added a new device") in each shared conversation when the new leaf joins, and the server sends `UserDevicesChanged` to friends. An enrolment made by someone who cracked the password therefore cannot go unnoticed.
- The recovery key is displayed once. It allows a password reset without losing the identity: the client unwraps the AIK with it, runs a new OPAQUE registration and uploads a new password-wrapped copy.

## Alternatives considered

- **Argon2id hash sent over TLS**: simple, but the server sees the password at every login.
- **SRP-6a**: no password on the wire, but the salt is public, which allows precomputation before a compromise; OPAQUE avoids that.
- **Passkeys only**: strong, but recovery and cross-platform keychain behaviour are not yet smooth enough to be the only method. Planned as an addition.
- **Linking a new device from an existing one** (QR code) instead of password-wrapped keys: stronger against server compromise, unusable when the only device is lost. Could be added later as an option for users who want it.

## Consequences

- The server never receives a password or a password-equivalent value.
- Someone who steals the database **and** the `ServerSetup` can still run an offline dictionary attack, at Argon2id cost per guess. Success yields the password and therefore the AIK. This is the residual risk of any password-based scheme; it is stated in the threat model and mitigated by the client-side strength requirement and by enrolment notices.
- Registration and login each take two round trips.
- Argon2id cost is paid on the client at each login, which affects the perceived login time on slow machines.
