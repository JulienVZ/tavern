# ADR 0002 — MLS (RFC 9420) via OpenMLS for all message encryption

- Status: accepted
- Date: 2026-11-13

## Context

Every conversation must be end-to-end encrypted: 1:1 direct messages, private groups (up to about 25 people), text channels of a server (up to the whole instance, about 40 users with several devices each) and the key agreement behind voice channels. Users have several devices. Members come and go, and a removed member must lose access to everything sent after the removal.

## Decision

Use **MLS (RFC 9420)** through **OpenMLS** (0.8 at the time of writing, with `openmls_rust_crypto` as the crypto provider) as the single protocol for all of these cases.

- Ciphersuite: `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`.
- One MLS group per conversation: one per DM, one per private group, one per text channel, one per voice channel. The MLS `group_id` is the conversation UUID.
- **Each device is one leaf.** A user with three devices has three leaves in every group they belong to.
- **Credentials.** Each account has an Ed25519 *account identity key* (AIK). A device's MLS credential is a basic credential carrying a device certificate: user id, device id and device signature key, signed by the AIK. Members verify this signature before accepting an Add, an Update or an external join. Safety numbers compare AIK fingerprints.
- **Wire format.** Handshake messages (proposals, commits) are sent as `PublicMessage` (signed, not encrypted); application messages are `PrivateMessage`. This lets the server validate and order handshake messages. It reveals group membership, which the server knows anyway because it routes messages.
- **The server is the Delivery Service and the Authentication Service.** It stores KeyPackages, keeps the public state of each group (ratchet tree and group context, no secrets), accepts exactly one commit per epoch (compare-and-swap on the epoch), and relays ciphertext. It never holds a group secret.
- **The server is an MLS external sender, for Remove proposals only.** Every group lists the server's dedicated signature key in the `external_senders` extension of its group context. When a member loses access (kick, ban, role change, revoked device, deleted account) the server immediately stops delivering to the affected devices and emits an external `Remove` proposal. The first online member device commits it automatically. OpenMLS supports this through `ExternalSendersExtension` and `ExternalProposal::new_remove`. Clients **reject any external proposal that is not a Remove**: the server can never propose an Add.
- **The external sender key is a dedicated Ed25519 key** used for nothing else. It is distinct from the session token secrets, the OPAQUE server setup and the LiveKit API secret. See "External sender key lifecycle" below.
- **New devices join by external commit** using the `GroupInfo` that every committer uploads with its commit. Members accept an external commit only if the joining leaf carries a device certificate signed by the AIK of a user who is already a member (DMs, private groups), or of a user the server lists as authorised (server channels, see consequences).
- Periodic update commits rotate leaf keys (interval configurable, default one week per device and group).

### External sender key lifecycle

- Generated by `deploy/scripts/init.sh`, stored as its own secret, included in `backup.sh` and `restore.sh`.
- Its public key is published by `GET /version` and in the gateway `Ready` message.
- **If the key is lost or replaced**, existing groups still list the old public key. External Remove proposals signed with the new key are rejected by every client, so server-initiated removals stop working for those groups. Nothing else breaks: messages still flow, members can still add and remove each other with ordinary commits, and the server still cuts delivery to removed devices at once. Confidentiality after a kick then depends on a member with the right permission committing the Remove itself.
- **Rotation procedure.** The operator adds the new key next to the old one (`TAVERN_MLS_EXTERNAL_SENDER_KEY` plus `TAVERN_MLS_EXTERNAL_SENDER_PREVIOUS_KEYS`, public parts only for the previous ones). The server advertises the new public key. Any member device that sees a group whose `external_senders` does not match the advertised set commits a `GroupContextExtensions` proposal that replaces the list. Once every active group has moved, the operator drops the old key. After a loss (no overlap possible) the same automatic commit repairs each group the next time one of its members is online.
- Clients accept the advertised key because it comes over the authenticated TLS session to their own instance. The key only grants the power to propose removals, which the server already has in practice by refusing to deliver.

## Alternatives considered

- **Signal protocol (Double Ratchet + Sender Keys)**: well understood, but group membership changes need pairwise fan-out, and removing a member requires every remaining sender to redistribute keys. Cost grows with group size and device count.
- **Matrix Olm/Megolm**: same family of trade-offs, tied to the Matrix data model.
- **A custom scheme**: excluded by project rules (no home-made cryptography).
- **Encrypted handshake messages**: hides the tree from the server but prevents it from validating commits against permissions and from knowing leaf indices for Remove proposals. The membership it would hide is already server-visible.
- **Removal committed only by a moderator's client**: no external sender needed, but a kicked member keeps receiving keys until a moderator is online. Kept as the fallback path.
- **Server as a full group member**: would let it commit removals directly, and would also let it decrypt everything. Rejected.

## Consequences

- The server depends on the `crypto` crate for signature, KeyPackage and public group state validation only. This matches the dependency rule in `CLAUDE.md`.
- Between the kick and the commit of the Remove, the removed device is still in the cryptographic group. It receives nothing from the honest server during that window, but a compromised server could still feed it ciphertext. Documented in the threat model.
- A compromised server can propose spurious removals (denial of service) but cannot add members to DMs or private groups. For server channels, the planned mechanism is an external commit authorised by server-side roles, so that a newcomer does not wait for a member to be online; every arrival is always displayed in the channel. A compromised server could therefore authorise a ghost account for future messages, and that arrival would be visible to every member. A "private channel" option, where joining requires an Add committed by an existing member, is planned for channels that need the stronger guarantee. The final decision is taken at M4.
- New members and new devices cannot read earlier messages ([ADR 0006](0006-no-prior-history-v1.md)).
- OpenMLS is pre-1.0; its API still moves between minor versions. The `crypto` crate wraps it completely so that upgrades touch one crate. The public group tracking API used by the server is to be confirmed against the pinned version at M2.
- The local MLS state is stored in the client's SQLCipher database (`openmls_sqlite_storage` or a storage provider of our own, decided at M2).
