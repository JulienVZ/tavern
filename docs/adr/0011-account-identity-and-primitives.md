# ADR 0011 — Account identity key, device certificates and cryptographic primitives

- Status: accepted
- Date: 2026-11-14

## Context

[ADR 0002](0002-mls-via-openmls.md) and [ADR 0003](0003-opaque-authentication.md) introduce an account identity key (AIK) that certifies devices and whose private half is stored by the server only in wrapped form. This ADR fixes the formats and the primitives used to build them, and records the dependencies added to the `crypto` crate at milestone M1.

No primitive is implemented in this repository.

## Decision

### Primitives and crates

| Purpose | Primitive | Crate |
|---|---|---|
| Account and device signatures | Ed25519, strict verification | `ed25519-dalek` 2.2 |
| Wrapping the AIK | XChaCha20-Poly1305 | `chacha20poly1305` 0.10 |
| Key derivation | HKDF-SHA512 | `hkdf` 0.12, `sha2` 0.10 |
| Token hashing | SHA-256 | `sha2` 0.10 |
| Password authentication | OPAQUE, Argon2id | `opaque-ke` 4.0.1, `argon2` 0.5 |
| Randomness | operating system generator | `rand` 0.8 (`OsRng`) |
| Erasing secrets, constant-time comparison | — | `zeroize`, `subtle` |
| Recovery key and codes as text | Crockford base32 | `data-encoding` |
| Password normalisation | Unicode NFKC | `unicode-normalization` |

`opaque-ke` 4.0.1 is built on the RustCrypto generation around `digest` 0.10. `ed25519-dalek` 2 and `chacha20poly1305` 0.10 are also what `openmls_rust_crypto` 0.6 uses, so they are shared. OpenMLS uses `hkdf` 0.13 and `sha2` 0.11: both generations of those two crates will coexist from M2, whichever we pick here. We follow the generation of `opaque-ke`.

### Account identity key

An Ed25519 key pair generated by the client at registration. The private half is never stored on a device: it exists in clear only in client memory, for the time needed to certify a device or to authorise a credential change, in a type that is erased when dropped and prints as `<redacted>`.

Public keys are rejected at parse time when they are not curve points or are small-order points.

### Wrapped copies (format version 1, 73 bytes)

```text
0x01 || nonce (24 bytes) || XChaCha20-Poly1305(seed) (32 bytes) || tag (16 bytes)
```

- "Password" copy: key = `HKDF-SHA512(OPAQUE export key, info = "tavern aik wrap v1 password")`.
- "Recovery" copy: key = `HKDF-SHA512(recovery key, info = "tavern aik wrap v1 recovery")`.
- Associated data: a label, the kind of copy and the AIK public key. A copy cannot be moved to another account or presented as the other kind.
- After decryption the client checks that the seed yields the expected public key.

### Device certificate

`tavern.identity.v1.DeviceCertificate`: a payload (version, account id, device id, device public key, issue time) serialised once, and the AIK's signature over a label and those exact bytes. Verifiers check the signature on the bytes received, then decode them.

The device id is chosen at random by the device, so that it can be certified before the server knows the device.

### Signatures

Every signed message is `label || 0x00 || (length as u32 big-endian || field)*`. Labels are distinct per purpose (`tavern device certificate v1`, `tavern device session v1`, `tavern credential update v1`), so a signature can never be reused for another purpose and fields cannot be shifted into one another.

### Recovery key

32 random bytes shown once as 52 Crockford base32 characters in 13 groups of four. Decoding ignores case, spaces and hyphens, and reads `O` as `0` and `I`/`L` as `1`.

### Tokens and codes

Session tokens (32 random bytes), invitation codes and TOTP recovery codes (16 random bytes, Crockford base32) are stored as SHA-256 hashes. A fast hash is sufficient because these values are long and random.

## Known advisory: RUSTSEC-2026-0387 (crypto-bigint 0.5)

`cargo deny` reports timing variability in `crypto-bigint` 0.5.5, fixed only in 0.7.6. The crate reaches us through `elliptic-curve` 0.13, on which `opaque-ke` 4 (including 4.1.0-pre.2) and `voprf` 0.5 depend. There is no compatible fixed version.

Analysis (2026-11-14):

- Our OPAQUE suite uses ristretto255 for both the OPRF and the key exchange. That arithmetic is implemented by `curve25519-dalek`. `crypto-bigint` backs the scalar types of the NIST curves in `elliptic-curve`, which our suite does not instantiate; from `elliptic-curve` we only use the hash-to-field message expansion, which works on digests.
- Verified on the binaries: an optimised build that runs a full registration contains no symbol from `crypto-bigint`. The unoptimised test binary, which exercises every OPAQUE flow, contains two symbols whose mangled names mention the crate; both are instances of generic helpers from other crates that happened to be compiled in its unit (`subtle::black_box::<u8>` and a `core::ptr::read_volatile` debug check). No arithmetic function of `crypto-bigint` is linked.

Decision: the advisory is ignored in `deny.toml` with this justification. A CI step rebuilds the measurement example without stripping and fails if any `crypto_bigint` symbol appears, so that a future change that starts using the affected code cannot go unnoticed. The exception is re-evaluated on every `opaque-ke` upgrade and at milestone M9.

## Alternatives considered

- **The newest RustCrypto generation everywhere** (`ed25519-dalek` 3, `chacha20poly1305` 0.11): would duplicate curve and cipher code next to what `opaque-ke` and OpenMLS already pull in.
- **AES-256-GCM for wrapping**: equally sound; XChaCha20-Poly1305 allows random 192-bit nonces without a counter.
- **X.509 or COSE for device certificates**: standard, but far more surface than five fields need.
- **BIP39 words for the recovery key**: easier to read aloud, but the maintained crate is CC0-licensed, outside the allowed list.
- **Signing a hash of structured data (as JSON or re-encoded protobuf)**: canonical encoding problems; signing the transmitted bytes avoids them.

## Consequences

- The wrapped key, certificate and recovery key formats are frozen by known-answer tests in `crates/crypto/src/identity.rs`. Changing them requires a new version number.
- `Debug` exists on secret types because test and error ergonomics need it, but it prints `<redacted>`; tests check it.
- Two generations of `hkdf` and `sha2` will be compiled into the client from M2.
- `opaque-ke` depends on an older RustCrypto generation; advisories are tracked through `cargo deny`.
